## Stuff I learned today

1. So I just had a big realization with how I've setup my backend validation system. I already knew that typescript infers types from my zod schemas to enforce types during development and compile. However, I realized that for stuff involving the database, like a custom data type (e.g. `Prisma Enum`), Prisma and Zod can actually share that custom data type in their respective schemas! woah! And of course typescript can infer from zod, who borrowed the custom data type from prisma, to enforce development/compile type safety.
2. Upon learning about prisma enums, I wanted to know what other custom data types prisma can use. And so I stumbled upon Prisma `Json` (JSONB), but a deep dive on that is for another. Although it's worth mentioning that jsonb allows for essentially stuffing a noSQL doc store in a postgres field! (Kinda like what I did with kanji wizard.)
3. I also learned that the third 'custom type' of Prisma are the good ol Prisma models that I already use (the relations).
4. So I guess I was confused about what JAMstack app was. It turns out my app is NOT JAMstack, and instead is a single page app that uses the PERN stack. Oops.
5. I went on a deep dive into JAMstack, old school monoliths, PERN SPAs, and Next.js apps. Here's a summary I wrote:
   > So it seems like the real magic of next.js over spa pern is:
   >
   > 1. You don't have to keep the entire react application in the browser. Only the exact pieces of your react app are brought it at a time, and they're brought it intelligently via chunks to minimize waiting. Which means code splitting for an spa pern app solves one of these pieces, BUT next.js also cuts out the step of having to do an http request to grab the data from the backend (because in next.js the database is right there for to grab and send off with the code chunks!)
   > 2. You don't have to store static pages in the client via a static react component/page because you can instead delegate serving that static page to a CDN
6. We don't usually need to log JWT errors (in our authenticate middleware via `jwt.verfiy()` failing) because jwt cookies expire all the time and we can just consider it normal behavior and not a bug, so logging all that stuff would just be useless noise.
7. Learned about `Conditional Spreading`. I can now used it in my `errorHandler` to check if the passed in `AppError` has a `fields` property (which as of today would only be sent in from our validate middleware). If it doesn't, there `fields` property simply isn't added to the error response object. If it does, it's added! This allows me to omit `| undefined` on the `fields` property of the interfaces ApiErrorDetail and ApiErrorResponse.
